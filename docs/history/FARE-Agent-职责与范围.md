# FARE：防火墙访问需求合规评估 Agent

> **FARE — Firewall Access Request Evaluator**  
> 依据既定网络合规规范，对防火墙网络开通需求进行自动预审与合规判定。

## 1. 工作职责

FARE 只回答一个核心问题：

> **这条防火墙访问开通需求是否合理、合规？**

它不是最终审批人，也不是防火墙策略配置工具。其职责是将一条聚合的网络开通需求拆分为具体访问关系，使用 LLM 深度理解申请语义、整理带原文引用的候选证据、召回可能适用的正式规则并生成整改建议，再由服务端结合 ACL 校验 API、权威网络事实和已维护的合规规则执行确定性判定，输出可解释的合规结论或待定结论。

建议结论仅使用以下两类：

| 结论 | 适用情况 |
| --- | --- |
| 合规 | 未发现违反已定义规范的情况。 |
| 待定 | 明确命中拒绝规则，或现有事实不完整、冲突、不确定，无法输出合规结论；必须附原因类型、原因编号和具体说明。 |

## 2. 输入与依据

### 2.1 网络开通需求

前置系统已完成字段完整性、格式和合法性校验。FARE 默认使用以下已校验字段：

- 源地址 IP / 网段及源地址说明
- 目的地址 IP / 网段及目的地址说明
- 协议
- 目的端口 / 端口范围

### 2.2 ACL 校验 API 返回信息

ACL API 用于补充访问关系的候选路径与配置分析证据，主要包括：

- 每个源—目的组合经过的防火墙
- 防火墙名称、接口或安全域标识
- 候选 ACL、地址对象 / 地址组、服务对象及相关配置片段
- 不同源、目的组合是否属于不同网络场景

首期 ACL API 返回的 `analysis/config` 属于路径与拟新增策略分析，**不是现网 ACL 状态**。FARE 不得据此输出“已命中 ACL”“现网已放通”或“无需新增配置”等结论；它们仅可作为候选路径与配置分析证据。

### 2.3 合规规则库

FARE 的判定必须以可维护、可追溯的规则为依据，规则可包括：

- 区域访问规则：如“办公区不得直连生产区”。
- 对象关系规则：如“办公终端不得访问生产数据库”。
- 特殊端口规则：如 Telnet 禁止、生产管理端口仅允许指定来源访问。
- 最小开放规则：如禁止 `any`、禁止全端口或明显过大的地址范围。

当前尚无已批准的区域访问限制条件，因此 `zone_relation` 规则只保留能力定义和测试夹具，不得把“办公区不得访问生产区”等示例直接发布为生产拒绝规则。区域目录仍可用于事实归类、冲突发现和未来规则扩展；在正式制度及审批信息进入规则包前，LLM 也不得自行补造区域限制。

未命中拒绝规则本身不构成待定；在事实完整且没有命中拒绝规则时输出“合规”。事实缺失、冲突或存在歧义时，FARE 不应自行猜测，应输出“待定”并说明原因。

### 2.4 LLM 语义分析

LLM 是每次评估的深度语义分析组件，批量处理申请说明、源和目的描述、ACL `analysis/config` 以及服务端提供的候选规则摘要，承担以下任务：

- 将访问目的、系统角色、环境、临时性、运维方式等非结构化描述整理为候选声明。
- 从 ACL 自由文本整理候选防火墙、接口、安全域、对象、服务和端口事实。
- 为每项候选声明保存来源字段、可定位原文、置信度和适用的访问组合。
- 召回可能适用的已批准规则编号，发现描述、目录、ACL 与规则之间的矛盾或覆盖缺口。
- 生成面向申请人和审批人的补充问题、解释和最小权限整改建议。

LLM 输出是候选语义层，不是权威事实层。模型不能返回最终 `decision`，不能创建规则，不能将未被权威目录或稳定结构化字段确认的区域、对象或业务关系用作“合规”依据。服务端必须验证原文引用、规则编号、输出枚举、子项覆盖和权威事实冲突；未通过验证的模型输出不得进入确定性判定。

## 3. 核心工作流程

1. 将一条含多个源、多个目的或多个端口范围的需求拆分为独立访问组合；组合键为“源地址范围 × 目的地址范围 × 协议 × 端口范围”。地址可为单 IP 或 CIDR 网段，单 IP 按 IPv4 `/32`、IPv6 `/128` 规范化。因权威目录而拆分出的子网段也必须保留与原申请的关联。
2. 查询权威网络目录和 ACL API，并用固定解析器整理可直接确认的结构化事实。
3. 将同一申请的全部访问组合批量交给 LLM 执行语义理解、候选事实整理、矛盾发现、正式规则召回和补充问题生成；所有候选声明必须带可定位原文证据。
4. 服务端对模型输出执行 Schema、证据、规则编号、权威事实和越权内容校验，并将结果标记为 `verified`、`candidate`、`conflict` 或 `rejected`。模型召回规则只增加候选集，不能排除服务端确定性匹配发现的规则。
5. 服务端以完整规则包、权威事实和通过守卫的候选疑点执行确定性判定。权威事实冲突、必要事实缺失或有证据但无确定规则可判的疑点均输出附原因的“待定”。
6. 在结论已经确定后，由 LLM 基于已确认事实和已命中规则生成解释与整改建议；该阶段失败时使用规则模板，不改变已确定结论。
7. 汇总子项结论：任何子项为“待定”时，整体为“待定”；全部子项为“合规”时，整体为“合规”。不同子项应保留各自的事实、候选语义、规则、原因和建议。

例如，`源A、源B → 目的C、目的D` 默认至少应按下列组合分别分析：

| 子项 | 访问关系 |
| --- | --- |
| 1 | 源A → 目的C |
| 2 | 源A → 目的D |
| 3 | 源B → 目的C |
| 4 | 源B → 目的D |

## 4. 仅包含的四类判定

### 4.1 网络区域访问关系

判定 `源区域 → 目的区域` 是否符合区域隔离规则。区域归属以 CIDR 网络目录和契约稳定、语义明确的 ACL 结构化字段为权威事实。申请网段跨越多个目录项、覆盖多个区域或产生不唯一重叠时，应拆分为可唯一识别的子网段；无法无歧义拆分时输出“待定”。

区域之间是否允许访问由确定性规则匹配完成，LLM 深度参与区域相关描述、ACL 安全域/接口文本、目录一致性和候选规则的语义分析，但不参与最终裁决。地址说明或 LLM 推断不能覆盖权威区域，也不能作为输出“合规”的依据。任何必须依赖 LLM 推断才能确认区域的组合均输出“待定”。

未来经审批后可配置的典型规则候选包括：

- 办公区不得访问生产区。
- 测试区不得访问生产区。
- 外联区不得访问核心生产区。
- 互联网区不得访问内部生产区。

### 4.2 源、目的对象关系

根据权威网络目录中的对象类型、环境和标签与已定义规则，判断对象组合是否合理；源、目的说明仅作为佐证和冲突检测，不能单独成为“合规”的依据。例如：

- 办公终端访问生产数据库：命中对应拒绝规则时待定，并标记为规则违规。
- 测试系统访问生产系统：命中对应拒绝规则时待定，并标记为规则违规。
- 普通业务服务器访问网络设备管理地址：命中对应拒绝规则时待定，并标记为规则违规。
- 生产应用服务器访问已定义的对应生产服务：可按规则判定。

此项不要求 FARE 推断复杂、未登记的业务调用关系。

### 4.3 特殊端口规则

FARE 不判断普通或非通用端口的具体业务用途，也不建立完整的端口—服务映射库。

仅当协议和端口命中规则库中明确维护的特殊端口时，执行专项规则。例如：

- 管理类：SSH、Telnet、RDP、VNC、SNMP、设备管理页面端口。
- 数据库类：Oracle、SQL Server、MySQL、PostgreSQL、Redis、MongoDB 等已登记端口。
- 明文或禁止类：FTP、Telnet、TFTP，以及由组织明确列管的其他端口。
- 自定义敏感端口：特定设备、系统或中间件管理端口。

未命中特殊端口规则的端口不进行业务用途判定，不因此产生风险结论。

### 4.4 最小开放原则

判定申请范围是否明显扩大访问权限，包括：

- 源或目的使用 `any`。
- 源或目的网段明显过大；阈值由规则库按地址族和前缀长度维护，不在程序中写死。
- 申请全端口或明显过大的端口范围。
- 多源、多目的全组合产生未证明必要的额外访问关系。
- 将不同区域或不同系统的访问场景不适当地合并到一条申请中。

## 5. ACL API 的边界与使用原则

ACL API 是 FARE 的重要事实来源，但不替代合规规范。

| API 信息 | FARE 的使用方式 |
| --- | --- |
| 候选路径中的防火墙、接口或安全域 | 辅助识别区域边界和拆分不同访问场景。 |
| 候选 ACL、地址对象、服务对象 | 辅助核实申请访问关系在分析结果中的表达。 |
| 明确未找到该访问组合经过的防火墙 | 在 ACL API 成功返回、结果可解析且明确表达无路径的前提下，输出“待定”，原因为 `acl_no_path`。 |

ACL API 调用失败、超时、响应无法解析、抽取器未找到防火墙名称或结果存在歧义时，不得等同于 API 明确返回“无路径”，应输出“待定”，原因为事实不完整或依赖失败。首期不得说明任何访问“现网已存在”或“现网已放通”。

## 6. 明确不在范围内

FARE 当前不负责以下内容：

- 输入字段完整性、IP / 网段 / 协议 / 端口格式与合法性校验。
- 普通端口或非通用端口的服务用途识别与合理性判断。
- 源 NAT、目的 NAT、NAT 前后地址分析。
- 堡垒机、代理、负载均衡、网关等中间节点或完整网络路径分析。
- 路由可达性、实际连通性、经过哪些完整网络设备。
- 现有 ACL 是否合理、是否过宽、是否应删除或整改；首期也不查询或判断现网 ACL 状态。
- 防火墙策略顺序、命中次数、配置优化，以及是否新增 / 修改 / 删除策略。
- 最终审批或例外审批决策。
- 让 LLM 自动发布规则、修改权威目录，或以模型置信度替代正式制度审批。

## 7. 单条需求输出要求

FARE 对每条需求应至少输出：

- 需求标识及拆分后的访问组合。
- 最终结论：合规或待定。
- 命中的规则编号 / 规则名称。
- 结论依据：需求字段、规则命中情况和使用到的 ACL API 候选路径与配置分析证据。
- LLM 语义分析结果：逐项候选声明、来源字段、原文引用、置信度、状态、适用组合、候选规则和规则覆盖疑点。
- 每个待定子项的 `reason_type`、`reason_code` 和具体原因；至少区分规则违规、事实不完整、事实冲突、无途径防火墙、依赖失败和风险不确定。
- 面向申请人的补充问题，以及基于已确认事实和已命中规则生成的可执行整改方向，例如缩小地址范围、拆分申请或补充权威事实。

调用方必须为每一个待评估的工单版本提供稳定且唯一的 `request_id`（建议使用评估记录 ID，而非仅使用工单号）。同一 `request_id` 的重放请求必须得到同一已完成评估结果，或在首次请求仍在执行时得到可重试的处理中响应；不同工单版本不得复用该标识。该约束用于使调用方在结果落库失败时能够安全重试，不改变 FARE 只返回“合规”或“待定”的业务结论边界。

输出应将“合规判定”与“ACL 候选路径/配置分析”分开呈现，且不得将后者表述为现网 ACL 状态或现网已放通。

## 8. 一句话定义

> FARE 将防火墙开通需求拆分为独立访问关系，由 LLM 深度理解申请与 ACL 文本、整理证据、召回正式规则并生成整改建议，再由服务端依据权威网络事实和版本化规则执行确定性判定。
