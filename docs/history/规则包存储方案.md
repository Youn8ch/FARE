# FARE 规则包存储方案

> [!NOTE]
> 历史文档（0.3.0 之前）：本文描述的候选路径/拟配置分析能力已在 0.3.0 完整移除，仅供历史追溯，不代表现状。现状见 README.md 与 docs/ARCHITECTURE.md。

## 1. 结论

FARE 运行时规则包建议采用“不可变版本目录 + YAML 清单 + YAML 规则文件”的形式存储。YAML 适合安全、网络和业务责任人共同评审；运行时仍必须经过严格加载器校验，不能把 YAML 当作任意表达式执行。

生产网段规划 `mock/http` 模式的规则包只包含规则和审批信息，不包含静态 `network_catalog.yaml`。静态目录只允许出现在显式 `offline_catalog` 兼容包和测试 Fixture 中。

当前系统只有 `合规/待定` 两种结论。因此规则名称中的“禁止”“不得开通”在运行语义上表示“命中后转待定并进入人工复核”，不表示自动拒绝，更不表示自动创建或下发防火墙策略。如果未来需要自动拒绝，必须先扩展对外 API、审批模型、审计和申诉流程，不能仅在 YAML 中增加 `拒绝` 值。

## 2. 当前测试资产

固定测试规则包保存在 `tests/fixtures/policies/`。每个目录都是可以由 `PolicyBundle.load()` 独立加载的规则包，目录内至少包含 `manifest.yaml` 和 `compliance_rules.yaml`；网段规划 API 模式的规则包不得包含 `network_catalog.yaml`。

已有 3 个基线有效规则包：

```text
network_plan_zone_relation/
network_plan_usage_relation/
network_plan_priority/
```

本轮新增 10 个有效规则包：

| 规则包目录 | 主要边界 |
| --- | --- |
| `network_plan_area_direction/` | areaId 正向命中、反向不命中 |
| `network_plan_region_relation/` | region 精确匹配、相邻 region 不误命中 |
| `network_plan_platform_relation/` | platform 精确匹配、同 area 其他平台不误命中 |
| `network_plan_usage_direction/` | usageCode 有向关系、空值不推断 |
| `network_plan_special_ports/` | TCP/UDP 协议边界、单端口和跨端口范围 |
| `network_plan_any_address/` | `any` 地址与普通地址边界 |
| `network_plan_prefix_limit/` | IPv4 前缀 `/23` 与 `/24` 阈值边界 |
| `network_plan_port_span/` | 端口数量 10 与 11 的阈值边界 |
| `network_plan_combination_count/` | 组合数 2 与 4 的阈值边界及输出顺序 |
| `network_plan_multi_condition/` | 多条件 AND 命中及源、目的条件近似但不命中 |

另有 4 个只能用于验证“加载失败”的无效规则包：

```text
network_plan_invalid_unknown_condition/
network_plan_invalid_empty_when/
network_plan_invalid_duplicate_id/
network_plan_invalid_decision/
```

对应的本地网络需求按组保存在 `tests/cases/network_plan_rules/`：

```text
any_address.requirements.json
area_direction.requirements.json
combination_count.requirements.json
multi_condition.requirements.json
platform_relation.requirements.json
port_span.requirements.json
prefix_limit.requirements.json
region_relation.requirements.json
special_ports.requirements.json
usage_direction.requirements.json
invalid_packages.json
```

其中 `*.requirements.json` 是有效规则包的网络需求组，`invalid_packages.json` 只保存无效规则包加载预期。测试程序只用明确的文件名模式扫描，不把无效包配置误当成网络需求。

## 3. 推荐目录结构

生产发布建议按版本保存为不可变目录：

```text
policy-bundles/
  2026.08.0/
    manifest.yaml
    compliance_rules.yaml
    usage_code_dictionary.yaml     # 可选，只有正式数据字典批准后才允许
```

当前运行时必需文件只有：

```text
manifest.yaml
compliance_rules.yaml
```

只有离线兼容模式额外包含：

```text
network_catalog.yaml
```

禁止在规则包中保存 API Token、密码、私钥、真实工单原文或未经脱敏的 ACL 响应。

## 4. manifest.yaml 格式

### 4.1 当前可运行格式

```yaml
version: "2026.08.0"
released_at: "2026-08-05"

sources:
  - id: NETWORK-ACCESS-MATRIX-2026
    name: 网络区域访问控制矩阵

approvals:
  - role: network-security-owner
    approver: example-owner
    approved_at: "2026-08-05"
```

当前加载器要求：

- `version` 非空。
- `released_at` 是 ISO 日期。
- `sources` 非空。
- `approvals` 非空。
- `offline_catalog` 模式下，manifest 版本必须与静态目录版本一致。
- `mock/http` 模式下，规则版本与网段规划事实版本解耦。

### 4.2 后续推荐扩展

以下字段适合作为下一版清单契约，但当前加载器尚未强制校验：

```yaml
schema_version: "fare-policy/v1"
version: "2026.08.0"
released_at: "2026-08-05"
effective_from: "2026-08-10T00:00:00+08:00"
supersedes: "2026.07.0"

files:
  compliance_rules.yaml:
    sha256: "<approved-file-digest>"
```

文件摘要用于证明审批后内容没有被静默替换。引入这些字段时应同步升级加载器和测试，不能只在文档中约定。

## 5. compliance_rules.yaml 格式

### 5.1 顶层结构

```yaml
rules:
  - id: ZONE-OFFICE-CORE-DB-001
    name: 办公网到核心生产数据库平台访问复核
    description: 办公网不得直接访问核心生产数据库平台
    category: zone_relation
    decision: 待定
    reason_type: policy_violation
    when:
      source_area_id: 本部办公区
      destination_area_id: 核心生产区
      destination_platform_name: 核心数据库平台
    semantic_keywords:
      - 办公网
      - 核心生产区
      - 数据库
    evidence_requirements:
      - source_area_id
      - destination_area_id
      - destination_platform_name
    reason_template: 办公网不得直接访问核心生产数据库平台。
    recommendation: 使用受控运维入口或进入正式例外审批流程。
    remediation_template: 改用受控运维入口并补充审批依据。
```

### 5.2 规则字段

| 字段 | 必需 | 约束 |
| --- | --- | --- |
| `id` | 是 | 包内唯一、长期稳定，不复用已废弃 ID |
| `name` | 是 | 面向评审人员的简短名称 |
| `description` | 是 | 说明规则依据和范围 |
| `category` | 是 | `zone_relation/object_relation/special_port/least_privilege` |
| `decision` | 是 | 当前只能是 `待定` |
| `reason_type` | 是 | 必须属于服务端白名单 |
| `when` | 是 | 非空对象；所有条件执行 AND 匹配 |
| `semantic_keywords` | 是 | 提供给 LLM 的候选语义提示，不参与确定性命中 |
| `evidence_requirements` | 是 | 声明规则需要的事实字段 |
| `reason_template` | 是 | 服务端规范原因，不允许 LLM 覆盖 |
| `recommendation` | 是 | 面向申请人的处理建议 |
| `remediation_template` | 是 | 规则治理和整改模板 |

## 6. 条件字段白名单

### 6.1 zone_relation

网段规划 API 模式优先使用：

```text
source_area_id
destination_area_id
source_region_name
destination_region_name
source_platform_name
destination_platform_name
source_usage_code
destination_usage_code
```

兼容字段：

```text
source_zone
destination_zone
```

推荐优先级为稳定编码 `areaId/platform code/usageCode`，其次才是展示名称。如果接口只提供中文名称作为 `areaId`，应先由接口责任人确认其稳定性，再将其写入生产规则。

### 6.2 object_relation

除区域字段外，离线或独立权威对象源还可以使用：

```text
source_environment
destination_environment
source_object_type
destination_object_type
source_labels
destination_labels
```

不得根据网段规划 `description` 自动生成 `object_type/environment/labels`。`usageCode` 与对象类型之间只有在正式数据字典批准后才能建立显式映射。

### 6.3 special_port

```yaml
when:
  protocol: tcp
  ports: [23]
```

`protocol` 和 `ports` 必须同时存在。端口命中规则是“申请范围包含该端口”，不是只有单端口申请才命中。

### 6.4 least_privilege

当前支持：

```yaml
when: {check: any_address}
```

```yaml
when:
  check: prefix_too_broad
  min_ipv4_prefix: 16
  min_ipv6_prefix: 48
```

```yaml
when:
  check: port_span
  max_ports: 100
```

```yaml
when:
  check: combination_count
  max_combinations: 64
```

`ACL-PATH-001` 是当前规则包必需的系统规则：

```yaml
when:
  explicit_no_path: true
```

## 7. 匹配语义和限制

- 同一条规则中的条件全部按 AND 匹配。
- 规则有方向性；`A -> B` 不代表 `B -> A`。
- 当前不支持通配符、正则、否定条件、嵌套表达式和列表型 OR。
- 需要 OR 时应拆成多个独立规则 ID。
- 缺失字段不会猜测；例如 `usageCode=null` 不会命中要求 `GENERAL_VM` 的规则。
- 多条正式规则可以同时命中，全部保存在 `matched_rules`。
- 当前同优先级正式规则的主原因取规则文件顺序中的第一条。生产使用前建议增加显式 `priority` 契约并进行冲突检测；在此之前，应把更具体的规则放在更通用的规则之前，并用测试锁定顺序。
- 网段规划 404、认证失败、依赖失败、非法响应和 IPv6 不支持优先于正式区域规则成为主原因；与网络事实无关的端口规则仍可作为附加命中保存。
- 规则包中的阈值是业务规则，命中后返回 HTTP 200“待定”；资源硬限制返回 HTTP 422，两者不能混用。

## 8. 测试网络需求格式

固定测试输入采用“一个 JSON 文件 = 一组网络需求”的本地存储方式。一组必须绑定一个独立规则包和一个网段规划 Provider Fixture，可以在 `cases` 中包含多条请求。JSON 避免了 YAML 隐式类型转换对 API 请求和预期结果的影响。

文件命名为 `<group>.requirements.json`，统一置于：

```text
tests/cases/network_plan_rules/
```

完整结构示例：

```json
{
  "fixture_version": "2026.08.0",
  "purpose": "areaId 方向性正反边界",
  "policy_dir": "tests/fixtures/policies/network_plan_area_direction",
  "network_plan_fixture": "tests/fixtures/network_plan/multi_region.v1.json",
  "cases": [
    {
      "id": "area-direction-positive",
      "request": {
        "request_id": "group-area-direction-positive",
        "sources": [
          {"address": "16.210.8.10", "description": "办公终端"}
        ],
        "destinations": [
          {"address": "16.220.16.20", "description": "核心数据库"}
        ],
        "protocol": "tcp",
        "ports": [{"start": 443, "end": 443}],
        "request_description": "办公区到核心生产区"
      },
      "expected": {
        "decision": "待定",
        "lookup_count": 2,
        "acl_call_count": 1,
        "accesses": [
          {
            "source": "16.210.8.10/32",
            "destination": "16.220.16.20/32"
          }
        ],
        "reason_codes": ["AREA-OFFICE-CORE-001"],
        "matched_rule_ids": [["AREA-OFFICE-CORE-001"]],
        "source_statuses": ["complete"],
        "destination_statuses": ["complete"],
        "acl_statuses": ["verified"]
      }
    }
  ]
}
```

格式约束：

- `fixture_version` 用于锁定测试数据契约版本。
- `policy_dir` 和 `network_plan_fixture` 必须是仓库内相对路径，禁止绝对路径和 `..` 跳转。
- 每组至少包含一个 `case`；组内及全目录的 `case.id`、`request.request_id` 都必须唯一。
- `request` 必须完整符合 `EvaluationRequest`，未知字段直接失败。
- `accesses` 及其后的 6 个数组按响应 `items` 的位置一一对齐，长度不一致直接失败。
- `lookup_count` 验证网段查询去重，`acl_call_count` 验证 ACL 调用次数。
- 测试输入、Provider Fixture 和规则必须一一对应；测试不得依靠 `description` 猜测区域或用途。
- 所有数据均为脱敏合成数据，只使用本地 mock，不访问真实网段规划、ACL 或 LLM 服务。

无效规则包单独使用 `invalid_packages.json`：

```json
{
  "fixture_version": "2026.08.0",
  "purpose": "规则包严格校验失败边界",
  "cases": [
    {
      "id": "unknown-condition",
      "policy_dir": "tests/fixtures/policies/network_plan_invalid_unknown_condition",
      "error_contains": "unsupported matching conditions"
    }
  ]
}
```

## 9. 必测边界矩阵

| 维度 | 正向 | 反向或边界 |
| --- | --- | --- |
| area 方向 | 办公网到核心生产区命中 | 核心生产区到办公网不命中 |
| 精确平台 | 核心数据库平台命中具体规则 | 同区域其他平台不命中具体规则 |
| 精确 region | 鲲鹏应用 region 命中 | 相同 area、通用计算 region 不命中 |
| 用途 | `GENERAL_VM -> PROD_DATABASE` 命中 | `usageCode=null` 不命中且不从描述推断 |
| 特殊端口 | TCP 22、TCP 23 命中 | UDP 22 不命中；21-23 范围同时命中两条规则 |
| 任意地址 | `any` 命中 | 普通主机地址不命中 |
| 前缀阈值 | `/23` 超过允许范围并命中 | `/24` 位于边界且不命中 |
| 端口跨度 | 11 个端口超过阈值并命中 | 10 个端口位于边界且不命中 |
| 组合数量 | 4 个访问组合超过阈值并保持稳定顺序 | 2 个组合位于边界且不命中 |
| 多条件 AND | 来源与目的的所有字段均匹配 | 仅来源或目的存在近似值时不命中 |
| 多事实聚合 | `/23` 同区域合并后命中 | 多区域 `/22` 分项独立裁决 |
| 失败优先级 | 成功事实执行区域规则 | 404/IPv6 成为主原因，端口规则仅附加保存 |
| 多规则 | 具体规则和通用规则同时保存 | 主原因顺序稳定 |
| Schema | 合法字段启动成功 | 拼写错误、空 `when`、重复 ID、非法 decision 启动失败 |

## 10. 发布流程

1. 业务和网络责任人提供区域访问矩阵及稳定字段数据字典。
2. 每个有方向的限制生成独立规则 ID；OR 条件拆分为多条规则。
3. 运行规则 Schema、未知字段、重复 ID、必需系统规则和冲突检查。
4. 使用脱敏 Provider Fixture 执行正向、反向、空值、多区域和失败优先级测试。
5. 生成文件摘要并完成审批。
6. 以新版本目录发布，不原地覆盖已审批版本。
7. 灰度观察命中率、待定率、404 率和规则重叠情况后切换。

大型区域矩阵可以由业务方在 Excel 或数据库中维护，但运行时不应直接读取 Excel。发布流水线应把已审批矩阵编译成上述严格 YAML 包，并把编译结果和摘要作为实际部署制品。

## 11. 当前测试基线

截至 2026-08-05，本方案对应的本地测试资产和验证结果如下：

- 13 个有效网段规划规则包可以独立加载，其中本轮新增 10 个。
- 10 个 `*.requirements.json` 网络需求组，共包含 22 条合成请求。
- 4 个无效规则包分别覆盖未知条件、空 `when`、重复规则 ID 和非法 `decision`。
- `tests/test_network_plan_rule_packages.py` 专项测试共 29 项，全部通过。
- 全仓 `python -m pytest -q` 共 336 项，全部通过。
- 全仓 `python -m ruff check .` 检查通过。

测试过程中只有第三方 `TestClient` 弃用提示和无权限创建 `.pytest_cache` 的环境提示，不影响规则包加载、请求执行或断言结果。
